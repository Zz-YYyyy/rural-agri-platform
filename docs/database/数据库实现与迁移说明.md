阅读入口：[数据库设计](数据库设计.md) → [完整字段字典](数据库字段字典.md) → 本文件。可执行结构仅维护在 [V1 SQL](../../backend/src/main/resources/db/migration/V1__initial_schema.sql)，不在 docs 再复制建表脚本。

## 本轮实施选择与范围

以下属于按用户“减少细枝末节讨论、先让项目能跑”的要求作出的开发设计，不新增 D 编号，也不声称用户逐项选过字段：

- 一个地区一份产地介绍，农户故事先放农户主页一份图文；使用受限 JSON 文字／图片块，不建设多篇文章社区。
- 同一咨询用户和同一农户共用一条异步留言会话，消息记录商品与推广来源；不引入 WebSocket、实时在线或独立采购意向表。
- 常规长度、图片上限、数据类型、索引、默认值与幂等标识在本轮确定。先保存推广浏览／咨询事件，通过 SQL 汇总；不另建统计中台或真实收益表。
- 原有 29 张表数量不变；图文编辑不重新引入人工审核，消费者 AI 导购继续保留。

仍需在对应接口／业务模块落实的实质问题：账号和经营禁用后的存量操作、微信换绑策略、专题条件不匹配后的结束历史归属，以及 AI 实际预算／提供方和数据保留周期。已有字段容纳历史或限制事实，不代表这些规则已被默认值选定；不得仅为“表能保存”就开放相应操作。

## 关系完整性、并发和删除

本版不声明物理外键，采用逻辑关联。这使版本化迁移和演示数据装载较简单，但数据库本身不会阻止悬空引用；Service 必须验证关联记录存在、归属和有效状态，修改在同一事务完成，禁止 Controller 直接把客户端整行对象交给 Mapper 保存。

核心账号、农户、商品、SKU 和字典记录有业务引用时不物理删除；用已定义的状态限制新操作，具体允许操作仍按业务规则。收藏、购物车和地址簿的本人删除不删除其引用对象；订单独立保存快照。日志是追加记录，普通更新接口不能修改；AI 记录的保留／清理需后续制定脱敏与用量核对策略，不因建表就无限保留。

并发采用 MySQL 事务和行锁，不引入分布式事务。业务使用固定顺序锁定目标，SKU 批量按 ID 升序锁定；遇到死锁整体回滚并以原幂等键做有限重试。涉及多订单的管理下架需明确批次和锁顺序，付款服务必须重新检查管理限制，使异步清理期间也不能付款绕过限制。Redis 缓存、限流和预算预留只辅助业务，不替代金额、库存和订单状态的持久化依据。

`request_id`、`operation_key` 等标识用于识别一次业务操作；同一标识必须对应同一操作者、目标和输入内容。唯一键冲突时读取原结果并核对语义，不盲目把“冲突”当成功，不用新随机键让重试重复扣减。具体请求头／DTO 字段在接口契约中统一。

时间窗口以事务校验时的服务端有效时间为准。订单有效付款条件为当前时间早于 `payment_deadline`；专题报名含开始、不含结束；到期扫描晚到不延长窗口。自然结束保存原有效截止，不能写任务实际运行时间。只追加事件使用业务有效时间及序号／ID 确定顺序，不仅依赖毫秒时间去区分同刻事件。

## 迁移使用边界

- 文件采用 Flyway 命名 `V1__initial_schema.sql`，只包含 29 个 CREATE TABLE，不含建库、切库、删表、清数据、演示账号或业务数据导入。不使用 IF NOT EXISTS 隐藏已有结构差异。
- **2026-11-20 已在用户确认的本项目专用 MySQL 8.0.46 空库执行 V1，Flyway 历史成功，原有数据库未改动。** Maven 与 Flyway 11.7.2 已接入；默认 bootstrap 排除数据库自动配置，dev 配置默认关闭迁移，本机专用 local-env 显式开启。V1 从此次应用起不可变，后续改表新增迁移。
- 后端初始化时选择并固定兼容的 MySQL 8.0、JDBC 驱动和 Flyway 版本，再配置到明确命名的专用开发数据库。先在空的隔离数据库运行迁移和回归，核对 29 表、索引和约束，再准备演示数据。
- 不把该文件直接导入已有业务数据库。MySQL DDL 不是可把整份文件整体回滚的普通业务事务；中途失败须检查已完成结构与迁移历史，不随意重跑、删除表或使用 repair 掩盖错误。
- 首次真正应用后 V1 视为不可变；变更通过 V2 等迁移。演示数据放独立 seed 目录，由明确的演示环境导入流程执行，不能混入结构迁移。
- 运行环境启用严格 SQL 模式，应用连接时间区设为 `+00:00`，读取／写入使用同一时间约定。CHAR/VARCHAR 长度、金额精度及日期范围错误应拒绝，不能静默截断。

## 账号、农户与商品的关联和实现约束

依据：FR-AUTH-001、FR-ROLE-001、FR-FARM-001 至 FR-FARM-004、FR-REGION-001、FR-PRODUCT-001 至 FR-PRODUCT-006、FR-INV-001、FR-INV-002。

- `user_wechat_binding.user_id`、`user_address.user_id`、`farmer_application.user_id`、`farmer_profile.user_id` 关联 `sys_user.id`。`farmer_profile.approved_application_id` 必须指向属于同一账号且已通过的申请。申请审核、建立农户身份和管理员日志同事务提交；锁账号行防止并发产生多份待审申请，`farmer_profile.user_id` 唯一键防止重复经营身份。退回后是否重提仍按 Q-FARM-001，不由申请表容量决定。
- `region_id`、`origin_region_id` 引用 `region.id`；`main_category_id`、`category_id` 引用 `product_category.id`。主营品类首版采用一个有效分类节点，这是实现选型。审批后更改农户资料不更改原申请快照。
- `product.farmer_id` 引用 `farmer_profile.id`，`product_sku.product_id` 引用 `product.id`。账号有效、经营有效、商品正常上架、未被管理限制、规格有效和库存足够需组合校验，不能单看一个状态字段。
- `sys_user.status` 与 `farmer_profile.status` 的 `ACTIVE / DISABLED` 分别是账号与经营状态；`is_admin` 为独立能力。注册请求不能写 `is_admin`。密码采用 BCrypt 哈希，登录名在服务端去除首尾空白并规范为小写。建表不创建任何默认管理员或默认密码。
- `farmer_application.status`：`PENDING` 待审核、`APPROVED` 通过、`REJECTED` 退回。终态审核人、时间必填；退回说明必填。`request_id` 是同用户内的提交幂等键，重复键不产生第二份申请，也不能以相同键提交不同资料。
- 微信绑定仅对 `app_id + open_id` 唯一，不把可空 `union_id` 当作一定存在或跨应用唯一。`user_id` 未设置唯一，不提前决定每账号微信绑定数量或解绑、换绑策略；接口开放前按 Q-AUTH-001 明确，不能因为表能容纳多行就直接提供多绑定。
- 地址簿可按本人归属增删改。默认地址切换时锁用户行，同事务取消旧默认并设置新默认；允许没有默认地址，但最多一个。订单存四项地址快照，不持有必须依赖地址簿存在的外键，删除或修改地址不影响订单。
- `region.parent_id` 和 `product_category.parent_id` 为自身关联。根节点为空，分类不限定层数；地区采用省、市、县区三级目录，实际数据来源在演示数据阶段补充，不导入伪造的“官方编码”。服务层校验无环、上级存在、地区层级连续。地区和分类的被引用节点不直接删除或变更树归属，目录调整联动规则尚未完善时不开放这类管理动作。
- `ACTIVE / DISABLED` 在目录表表示可否用于新的选择；被停用节点仍可按 ID 读取历史名称，不能由停用直接推出所有旧商品或专题失效。相关联动按 Q-CONTENT-001、Q-CAMPAIGN-001 落实。
- `product.listing_status` 的 `ON_SHELF / OFF_SHELF` 与 `admin_blocked` 独立。商品发布流程可在事务内创建资料、至少一个规格并设为 `ON_SHELF`；数据库初始默认 `OFF_SHELF` 避免残缺商品外露，不新增需用户确认的商品草稿模块。管理强制下架要按 FR-PRODUCT-006 关闭涉及的未付款整单并返还其所有明细库存。
- 商品图片 `image_keys` 为 1～9 个非空资源 key 的有序数组，第一张封面；例如 `["uploads/product/demo-1.jpg"]`。9 张是本轮表单上限设计，不是历史用户指定。后端校验资源确由允许的上传入口产生、不含密钥或路径穿越。`season_months` 为空或 1～12 的去重整数数组，例如 `[9,10,11]`；NULL 和空数组都按未填写处理，写入统一使用 NULL。
- `story_content` 使用可空有序 JSON 图文块数组，例如 `[{"type":"text","text":"果园介绍"},{"type":"image","key":"uploads/story/demo.jpg"}]`。首版把故事放农户主页一份内容，文本块和图片块白名单渲染，服务端限制最多 50 块、合计文字 10000 字；不接受任意 HTML、脚本或模型输出作为可信节点。故事可不填写，不增加入驻条件。这是按简化实现原则选定的结构，不新增文章社区或用户业务决策编号。
- `product_sku.status` 的 `ACTIVE / INACTIVE` 表示规格能否供新购买选择；对被订单引用的规格不物理删除，停用和旧订单可操作范围仍见 Q-PRODUCT-001。规格名称只是标签，不从“3斤装”自动解析重量。`price` 为正的每份人民币价格；库存非负且按份计，不把斤数当份数。
- 新建规格的初始库存也写 `stock_log`；之后只接受库存增减操作，不能通过更新整个商品对象覆盖 `available_stock`。SKU 更新采用行锁或带库存条件的原子更新；事务中的锁顺序和库存幂等见交易约束。

## 交易、库存与评价

### 通用实现约定

- 金额均为人民币元，`DECIMAL(12,2)`，Java 使用 `BigDecimal`，禁止浮点算金额。本版商品单价采用大于零的常规校验；运费允许为零。数量为按规格计算的正整数份数，不把“斤”“箱”等规格文案自动转换为库存单位。
- 所有时间按 UTC 写入 `DATETIME(3)`，应用和数据库连接统一时区，展示时转换为北京时间。应用对一次状态变化只取得一次毫秒精度服务端时间，用它同时写业务时间和截止时间。
- 订单创建时显式写入同一个 `created_at` 和由它计算的 `payment_deadline`，避免先用应用时间算截止、再由数据库另一时刻生成创建时间导致精确时间 CHECK 失败。退款初次申请同理，`stage_started_at = created_at`。
- 没有物理外键。应用验证对象存在、归属和权限；有订单引用的商品、规格、农户和账号不得物理删除导致历史失去关联，使用状态限制。退款、订单明细、库存与业务流水、评价保留历史。收藏取消和购物车移除可删除对应行。
- CHECK 验证单行基本合法性，不替代跨表事务和状态迁移校验。`stock_log`、`order_action_log` 只追加，不覆盖旧事件。状态更新采用订单行锁及事务内检查，不能以 Redis 值决定库存、金额或最终状态。
- 可空编号的唯一索引允许多行 NULL，表示尚未发生支付、退款或发货。生成编号必须包含明确的模拟前缀，如 `MOCKPAY`、`MOCKREFUND`、`DEMO`，界面也明确标识模拟。

### 逻辑关系与查询方向

| 表 | 逻辑关系与用途 | 主要唯一约束和索引 |
| --- | --- | --- |
| `stock_log` | 每条归属一个 `product_sku`；订单扣减、返还关联一条 `order_item`；人工操作者关联 `sys_user` | `business_key` 唯一；同一订单明细同一变动类型唯一；按规格和发生时间查流水 |
| `user_favorite` | 用户收藏一个商品，不按规格收藏 | `(user_id, product_id)` 唯一；按用户与时间分页 |
| `cart_item` | 用户选择一个规格，商品及农户由规格关联查询 | `(user_id, sku_id)` 唯一；按用户与调整时间查询 |
| `trade_order` | 一个买家、一位农户、多个订单明细；地址是快照，不引用可随时删除的地址簿记录 | 订单编号、用户请求键、模拟支付号、演示单号唯一；买家与农户订单列表、待付款超时和待收货扫描索引 |
| `order_item` | 关联订单、原商品、原规格；保留下单名称、规格、图片、单价和数量 | `(order_id, sku_id)` 唯一；商品或规格反查关联订单 |
| `refund_request` | 一个订单可保存多次历史申请；申请账号须等于订单买家；处理者为账号 ID | 申请编号、用户请求键、模拟退款号唯一；订单历史、阶段超时、复核到期及处理人待办索引 |
| `order_action_log` | 始终关联订单；退款动作额外关联对应退款申请 | `business_key` 唯一；按订单或退款申请与时间查询 |
| `order_review` | 关联已完成订单及其买家、农户；回复者为该农户所属账号 | `order_id` 唯一；农户公开评价与买家评价查询索引 |

`order_item.product_id` 必须等于 `product_sku.product_id`，其农户必须等于订单 `farmer_id`；这些跨表等式在创建订单事务中校验。`order_review` 的买家与农户是订单归属的查询冗余字段，创建后不可独立修改。

### 库存与购物车

`product_sku.available_stock` 是唯一的可售库存持久化依据。`order_item.stock_status` 有两种取值：

| 状态 | 含义 |
| --- | --- |
| `OCCUPIED` | 下单时已从可售库存扣除，尚未返还；支付、发货、正常完成后仍保持此值，不表示订单仍在等付款 |
| `RELEASED` | 关闭未付款订单或成功发货前退款时已返还；保存首次返还时间，不再重复返还 |

`stock_log.change_type`：`INITIAL` 为规格创建初始库存，允许初值零；`ORDER_RESERVE` 为下单预占，增量为负；`ORDER_RELEASE` 为整单关闭或退款返还，增量为正；`MANUAL_ADJUST` 为农户对可售库存填写非零增减量。每条满足“变动后 = 变动前 + 增减量”，前后库存均不能为负。

建议库存幂等键为 `INIT:{skuId}`、`RESERVE:{orderItemId}`、`RELEASE:{orderItemId}`、`ADJUST:{userId}:{requestId}`。`(order_item_id, change_type)` 的唯一约束进一步阻止调用方换请求键后重复扣减或返还；人工调整的订单明细为空，不影响多次合法调整。初始化时由服务端使用唯一规范键，不能换键重复登记同一规格的初始库存。

库存修改、订单明细标记、库存流水和订单状态必须位于同一个数据库事务。读取并锁定规格后计算变动前后值，或执行带 `available_stock >= quantity` 条件的扣减并校验影响行数；多规格统一按 ID 升序处理，减少交叉下单死锁。任何一步失败整体回滚，不留下已扣库存的半张订单。

为保证旧单取消或成功退款仍可正常返还，库存容量按 `A + R <= 2147483647` 校验，而不只限制当前可售量 A。R 是同一 SKU 中 `stock_status = OCCUPIED`、所属订单状态为 `PENDING_PAYMENT / PENDING_SHIPMENT` 的明细数量合计，含退款处理中和已超时但尚未关闭的订单；已发货和已完成订单虽仍标为 OCCUPIED，但首版不能返还，不计入 R。R 从已有订单与明细计算，不新增表或持久化库存字段，也不向客户端提供改写入口。

人工增减使用宽整数求和与加减，在同一事务校验 `A + delta >= 0` 和 `A + delta + R <= INT_MAX`，失败不更新库存或写流水；超过返还容量返回 `STOCK_RANGE_EXCEEDED`。调整事务采用 READ COMMITTED，取得 SKU 行锁后读取最新已提交的 R，不使用加锁前的查询结果或可重复读旧快照。下单、关闭、成功退款和发货等改变 A 或 R 的流程，在提交相应明细／订单变化前也持有同一 SKU 行锁，多规格按 ID 升序锁定并与既有订单锁顺序保持一致；人工调整只读聚合，不反向锁订单，避免与先锁订单的履约流程形成新增锁顺序。

下单使 A 减少、R 等量增加，取消或成功退款使 A 增加、R 等量减少，发货只减少 R；这些动作均保持或降低合计容量。新增库存仅在合计容量有余量时成功，因此不能先将可售补满、再让既有订单返还时超出 INT 范围。所有运算在写回 INT 前完成范围校验，拒绝截断或整数回绕；这属于存储容量约束，不改变订单库存归属或原退款规则。

购物车只保存选定规格和份数，不存锁价，不占库存。加入同规格时合并，取消收藏或删除购物车不改变订单。下单时重新检查当前规格、商品上架状态、管理限制、农户经营权限、价格和库存，并按一个农户创建一张订单；无需把整个多农户购物车变为跨农户整单。

### 订单状态及快照

| 状态 | 含义与后续动作 |
| --- | --- |
| `PENDING_PAYMENT` | 下单成功并已占库存；截止之前可模拟支付、取消或按已有规则修改订单地址 |
| `PENDING_SHIPMENT` | 已模拟支付未发货；允许范围内可申请退款，退款相关暂停规则由退款表判断 |
| `PENDING_RECEIPT` | 已有效模拟发货；可手动确认收货，到计划时间后可系统确认 |
| `COMPLETED` | 用户或系统实际确认收货完成；在实际完成后 30 天内可首次评价 |
| `CLOSED` | 未付款整单已取消或关闭，所有明细库存已返还 |
| `REFUNDED` | 发货前整单模拟退款成功，所有明细库存已返还，正常履约结束 |

正常链路是待付款 → 待发货 → 待收货 → 完成；未付款可以关闭，已付款未发货可以经过退款流程最终变为已退款。退款处理中订单保留 `PENDING_SHIPMENT`，不可把申请退款等同于退款成功。

- 明细按同一 SKU 合并，保存 `product_name`、`spec_name`、`cover_key`、`unit_price`、`quantity`、`line_amount` 快照。`line_amount = unit_price × quantity`，所有明细小计之和等于订单 `goods_amount`。
- `shipping_amount` 复制农户当时的固定每单运费；`payable_amount = goods_amount + shipping_amount`。成功支付时 `paid_amount = payable_amount`，后续改价、改运费不改已有订单。
- `payment_deadline = created_at + 30 分钟`。模拟支付要求服务端当前时间严格小于截止时间；达到或超过即不可支付。定时任务晚运行不延长付款时间，支付入口也必须校验截止并按事务处理超时关闭。
- 付款只更新状态、模拟支付号、支付金额和时间，不再次扣减库存。未付款关闭原因有 `USER_CANCEL`、`PAY_TIMEOUT`、`ADMIN_PRODUCT_OFFLINE`；管理员强制下架涉及某商品时关闭包含该商品的相关未付款整单，并返还该单所有商品，不只返还目标商品。
- 农户主动下架不自动关闭已有未付款订单；在原有效期内依然允许按下单金额支付。支付检查须区分当前商品禁止新下单与订单已获得的有效付款资格，不能以“现在不在售”一概拒绝旧单支付。
- 收货快照包含姓名、手机号、地区 ID、完整地区名称、详细地址。只有有效未付款订单允许买家主动更新这些地址字段；修改地址簿不自动同步旧单。修改不改变金额、`created_at` 或付款期限。备注在创建时固定。
- 模拟发货填承运方、生成唯一演示单号，写 `shipped_at` 和 `auto_receive_at = shipped_at + 7 天`；先确认没有有效退款阻止发货。物流只展示演示节点，不接真实查件。
- 完成时写真实生效的 `completed_at`、来源 `USER` 或 `SYSTEM`，以及 `review_expires_at = completed_at + 30 天`。系统延迟运行时以实际完成时间起算评价期限，不能用计划自动收货时间回填。重复确认保持首次结果，不延长评价窗口。

下单幂等通过 `(user_id, client_request_id)` 唯一键实现。`request_fingerprint` 是规范化原始结算请求的 SHA-256 小写十六进制摘要，包含所选 SKU 和份数、农户、用户提交的地址选择或地址内容以及备注；不包含实时重新查询出的价格、库存或时钟。相同用户与请求键、相同摘要返回已创建订单；同键不同摘要返回重复键冲突，不覆盖订单。金额由服务端当时快照决定。地址后续通过专用操作更改，不更新原请求摘要；重试结算也不重写地址。单靠捕获唯一键异常后再次插入无法防止重复扣库存，整个创建事务应回滚后读取已存在结果。

### 退款阶段、时间及结束原因

| 退款状态 | 订单与发货效果 | 后续处理 |
| --- | --- | --- |
| `FARMER_PENDING` | 订单待发货，暂停发货，库存保持占用 | 农户同意、农户拒绝、用户撤回；超过 48 小时可管理员接手 |
| `APPEAL_WINDOW` | 农户已拒绝，24 小时窗口内继续暂停发货 | 买家在截止之前申请管理员复核；过期转最终不退款 |
| `ADMIN_PENDING` | 用户复核或管理员接手，继续暂停发货 | 管理员同意、拒绝或买家撤回；超时只标记，不自动处理 |
| `REFUNDED` | 订单转已退款，整单返还库存一次 | 终态，不能撤回或继续发货 |
| `REJECTED` | 本次退款最终不退，订单仍待发货，恢复符合条件的发货权限 | 终态，不自动发货，也不返还库存 |
| `WITHDRAWN` | 买家撤回本次待处理流程，订单仍待发货，恢复符合条件的发货权限 | 终态，不退款、不返还库存 |

退款仅适用于本人已支付、未发货订单，`amount` 必须等于订单原 `paid_amount`，包含商品款和运费，不接收客户端任意退款金额。申请本身不返还库存，退款最终成功时才将订单转 `REFUNDED`，写入模拟退款流水号与时间，并在同一事务返还全部明细。

农户拒绝须保存 `farmer_rejected_at`、`farmer_reject_reason`、`appeal_deadline_at = farmer_rejected_at + 24 小时`；这是拒绝意见与复核机会，尚未形成可以发货的终态。买家必须在服务端时间 `< appeal_deadline_at` 时成功申请复核。

管理员阶段明确区分：

| `admin_entry_type` | 数据含义 |
| --- | --- |
| `USER_APPEAL` | 真实用户复核；保留农户拒绝，`appealed_at` 为实际复核时间且早于截止，`admin_entered_at = appealed_at`，不填写接手人 |
| `TIMEOUT_TAKEOVER` | 农户待处理超过 48 小时被管理员人工接手；`admin_entered_at` 为实际接手时间，`taken_over_by` 为管理员；农户拒绝、复核时间、复核说明保持空，不伪造用户动作 |

`current_handler_user_id` 在农户待审时为订单农户账号，进入用户复核的管理员公共队列时可为空，超时接手后保存实际接手管理员。它表达待办分配，不授予越权操作能力，也不覆盖原申请者和历史操作人。进入窗口和终态时可以清空当前处理人。

`stage_started_at` 在农户待审为原创建时间，复核窗口为农户拒绝时间，管理员待审为真实进入管理员阶段时间，终态为流程结束时间。当前农户或管理员待处理阶段严格超过 48 小时后可写 `overdue_marked_at` 并记 `REFUND_OVERDUE`；不改变审核结论、不退款、不返库存、不恢复发货。换阶段清空当前超时标记，先前阶段与超时证据保存在业务事件中，原 `created_at` 永久保留。

终态原因 `end_source`：

| 原因 | 对应状态及含义 |
| --- | --- |
| `FARMER_APPROVED` | 农户同意，`REFUNDED` |
| `ADMIN_APPROVED` | 管理员同意，`REFUNDED` |
| `ADMIN_REJECTED` | 管理员不支持退款，`REJECTED`，处理理由必填 |
| `APPEAL_EXPIRED` | 到期未申请复核，`REJECTED`，`finished_at` 记窗口实际截止，`finished_by` 为空 |
| `USER_WITHDRAWN` | 买家从农户待审或管理员待审撤回，`WITHDRAWN`，记录买家及时间 |

成功退款的 `refunded_at = finished_at`，订单 `refund_completed_at` 与之同刻。自动过期可因扫描延迟晚入库：`finished_at`、事件 `occurred_at` 记录有效截止，事件 `created_at` 记录实际入库时刻；过期处理不自动发货。退款窗口是否已经失效应在发货事务再次检查，不能只看异步扫描是否已修改状态。

同一订单同时最多一个活动退款流程，并且最多一次成功退款。首版不用生成列或额外表表达条件唯一性，统一先锁 `trade_order`，在该事务内查 `refund_request` 活动／成功记录再创建或变更；申请、发货、拒绝、复核、接手、撤回和退款成功采用同一个订单锁顺序，避免“已发货又接受发货前退款”或重复释放库存。退款行不能设置永久唯一 `order_id`，否则会把尚未确认的历史申请限制写死。**2026-11-20 已按 FR-REFUND-007 确认：撤回、复核到期或管理员拒绝后，仍已付款未发货且无活动退款时可创建新一轮申请；每单最多成功退款一次。新轮保留独立ID、时间和幂等键，不覆盖旧历史，也不能以旧请求操作新轮。**

### 业务日志及 JSON 数据约定

`order_action_log.action_type` 分组如下，操作须与同事务中的有效业务结果一致，不为失败重试伪造成功流水：

- 订单：`ORDER_CREATED` 创建；`ADDRESS_UPDATED` 修改有效未付款订单地址；`MOCK_PAID` 模拟付款；`USER_CANCELLED` 买家取消；`PAYMENT_EXPIRED` 未付款超时；`ADMIN_CLOSED` 管理员强制下架联动关单；`MOCK_SHIPPED` 模拟发货；`USER_RECEIVED` 用户确认；`AUTO_RECEIVED` 系统确认。
- 退款：`REFUND_APPLIED` 申请；`FARMER_REFUND_APPROVED` 农户同意；`FARMER_REFUND_REJECTED` 农户拒绝进入窗口；`REFUND_APPEALED` 用户复核；`REFUND_APPEAL_EXPIRED` 复核窗口过期；`REFUND_TAKEN_OVER` 管理员接手；`ADMIN_REFUND_APPROVED` 管理员同意；`ADMIN_REFUND_REJECTED` 管理员拒绝；`REFUND_WITHDRAWN` 撤回；`REFUND_OVERDUE` 阶段超时待办。
- 评价：`REVIEW_SUBMITTED` 首次评价；`REVIEW_REPLIED` 首次回复。评价及回复的管理员隐藏／恢复详情归入 `admin_operation_log`，不与订单状态变化混用。

日志保存订单前后状态；仅退款动作填写退款关联及前后状态。订单创建没有前态，首次退款申请没有退款前态，其他事件填写已有前态。同一提醒事件的幂等键应包含退款 ID、阶段和阶段起点，例如 `REFUND_OVERDUE:{refundId}:ADMIN_PENDING:{stageEpochMs}`，不能只用退款 ID，否则管理员阶段的新超时会被此前农户阶段日志拦住。进入终态先记录原阶段起点和原超时标记，再更新当前字段。

`event_data` 为选填 JSON 对象，例如：

```json
{
  "previousStage": "FARMER_PENDING",
  "previousStageStartedAt": "2026-11-19T02:00:00.000Z",
  "previousOverdueMarkedAt": "2026-11-21T02:01:00.000Z",
  "adminEntryType": "TIMEOUT_TAKEOVER"
}
```

只保存必要业务字段。地址修改事件记录动作与时间即可，不复制完整地址和手机号进日志；不保存模型密钥、密码、令牌、完整私人请求报文。金额如需进入 JSON 使用十进制字符串，时间统一 ISO 8601 UTC。数据库检查对象类型，服务端限制允许字段和数据大小；不能把 JSON 当作任意内容的附件仓库。

### 整单评价、匿名与一次回复

订单真实完成之后、服务端当前时间严格早于 `review_expires_at` 时允许买家首次提交评价。服务端在锁定订单后检查买家、完成状态与时间，`order_id` 唯一约束阻止并发重复。已提交的有效请求重试返回原结果，不因后续超时或管理隐藏创建新评价。用户从未评价时，不生成默认好评。

`rating` 是该次整体购物体验的整数 1～5 星，不展开成每个商品或规格的评分。文字选填，`image_keys` 为最多 3 个受控资源标识的 JSON 字符串数组：

```json
["review/2026/11/example-a.jpg", "review/2026/11/example-b.jpg"]
```

数据库检查数组及最大个数；服务端检查每项是有效字符串、资源存在、上传归属和允许公开展示，不直接接受任意外部 URL。未上传用 NULL 或空数组统一响应为无图片。买家提交后不能修改／删除；评价内容与图片不会被隐藏操作改写。

农户最多一条文字回复，`reply_content`、`reply_user_id`、`replied_at` 同时由空变为有效值。使用条件更新或评价行锁保证只成功一次；发布后不能修改／删除，不做多轮对话，也不另设首次回复时间上限。是否允许对被隐藏评价首次回复仍属 Q-REVIEW-001，本表不以隐藏标记自行授权。

公开列表集中在农户主页，商品详情只提供“查看农户评价”入口。公开评价接口统一输出“匿名用户”和默认头像，不返回真实买家昵称、头像、手机号或用户 ID；表内真实关联保留用于订单归属验证和授权管理查询。

`review_hidden` 与 `reply_hidden` 是独立管理标记。公开回复要求父评价可见且回复自身可见；隐藏父评价不会覆盖回复自己的隐藏标记，恢复父评价也不能把本来独立隐藏的回复自动恢复。每次隐藏或恢复都须保存当前操作人、时间、非空原因，同时写追加式管理员操作日志；恢复后保留最近管理元数据，不能清空历史。隐藏不重置评价或回复次数。私有订单详情可见内容、原因展示与隐藏后首次回复的未决权限，不能由公开查询规则推导。

## 助农与内容

### 共用约定与逻辑关联

- MySQL 8.0.16+；InnoDB、utf8mb4、utf8mb4_bin；有符号 BIGINT 自增主键。DATETIME(3) 保存 UTC，应用在连接和序列化层统一 UTC，页面按北京时间展示。DDL 不含建库、切库或会话设置。
- 不创建物理外键。服务在事务中验证所有引用存在、归属正确、状态允许；历史引用不因关联对象下架而删除，不使用级联删除。SQL CHECK 只保护单行有效值，不能替代权限、跨表关系、不可变字段和操作顺序检查。
- `campaign.region_id` 关联 `region.id`、`category_id` 关联 `product_category.id`，各自空值表示不限，均填写时取交集；节点包含自身和后代。判断依据为商品当前地区／分类，不使用农户资料代替。
- `campaign_product.campaign_id/product_id` 分别关联专题和商品；农户归属从商品读取，不再复制一个可能不一致的 `farmer_id`。`campaign_participation_log` 关联该关系记录。
- `assistance_post` 分别关联 `farmer_profile` 和 `product`，验证商品确属该农户。所有操作账号字段关联 `sys_user.id`。`origin_content.region_id` 关联地区，唯一键实施一地区一份介绍。
- 资源字段只存受控对象 key，例如 `uploads/demo/fruit-cover.jpg`；资源访问 URL 在接口层组装，不保存外部密钥或临时签名 URL。可选普通字符串以去除首尾空白后空值归一为 NULL。
- 标题最多120字，专题介绍／推广说明最多5000字，原因最多500字，供货说明最多255字，属于本轮常规字段设计参数，不冒充此前用户逐项确认。

### 专题生命周期与整体隐藏

`publication_status` 只用 `DRAFT` 和 `PUBLISHED`。页面的即将开始、进行中、自然结束、提前结束由发布时间、计划起止和首次结束事实计算，不另存会与时间漂移的第三套阶段字段。

- 草稿允许标题、介绍、开始和结束分别未填写；已填写资料仍校验合法性，两端时间都有值时须开始早于结束。草稿不公开，不因到达计划开始自动发布。
- 发布事务锁定专题并校验管理员、必填资料及 `S < E`、有效发布时刻 `P < E`。`S <= P` 合法，实际报名最早为 `max(S,P)`，不补记过去参与。专题没有统一天数上限。
- 发布成功后计划起止、地区／分类条件、首次 `published_at` 不再可写；普通编辑仅按接口允许更新说明字段。CHECK 无法比对旧行，必须用专用更新语句和状态／版本条件落实，不开放任意实体覆盖。
- `end_source=NATURAL` 时 `ended_at=planned_end_at`，操作者和理由为空；`ADMIN` 时必须在有效进行中提前结束，保存管理员和必填原因，原计划时间保留。结束结果只允许首次有效落库，不能重开。
- 读取或修改时若无更早结束结果且当前时间已经达到原截止，按自然结束判断；任务尚未运行不意味着仍可报名。请求到达截止后不能补写一次新的提前结束。自然到期事务不改写 `updated_by` 为虚构管理员，结束来源及管理日志区分系统操作。
- `is_hidden` 与结束事实独立。隐藏可作用预告、进行中或已结束的已发布专题，禁止公开内容与报名；计时、参与和结束历史继续存在。解除清空本轮隐藏字段，但不清空结束或商品移除限制。隐藏和解除的完整操作历史由既有管理员日志同事务保存。
- `version` 每次有效变更递增；解除隐藏携带期望版本并在锁内核对当前一轮，避免迟到解除误清后来的新隐藏。重试不得改写首次发布、首次结束或当前隐藏轮次。

### 专题参与、限制和事件

关系表按专题＋商品唯一，代表一个长期存在的关系。首次加入轮次为1；合法重报在原关系行递增轮次，不能另造第二份当前关系。每次业务变化同时追加日志，历史记录不可更新或删除。

| 枚举／字段 | 含义与流转 |
| --- | --- |
| `JOINED` | 保留有效参与关系；当前可能因商品下架、不匹配或专题整体隐藏而不可见 |
| `EXITED` | 农户主动退出；条件允许时可立即重报，不套七天等待 |
| `REMOVED` | 管理员移出后的参与结果；限制解除后仍保持此状态，直到农户主动合法重报 |
| `is_join_blocked=1` | 当前专题对该商品存在移除禁报限制；须保存移除事件序号、管理员、时间和原因 |
| `JOIN` | 首次加入或新一轮重报，更新加入时间并清空离开时间 |
| `EXIT` | 当前轮农户主动退出，记录离开事实 |
| `REMOVE` | 管理员移出并形成限制，原因必填 |
| `UNBLOCK` | 解除指定一轮限制，不变更为 JOINED，不刷新加入或离开时间 |
| `PRODUCT_CONTEXT_CHANGED` | 商品产地／分类／上下架等用于展示判断的事实发生变化，保留同一参与轮次 |
| `actor_type` | USER 为平台用户／农户、ADMIN 为管理操作、SYSTEM 为系统任务；系统账号引用为空，其他不能为空 |

`event_seq` 是关系内单调递增序号，首次为1；唯一键防止同一序号重复落库。`blocked_event_seq` 标识具体的有效移除轮次，解除必须核对目标轮次，不能只按“当前有无禁报”处理旧请求。`operation_key` 在同一关系内唯一，同一请求重试复用；一次商品修改影响多个专题时，各关系可以复用该修改操作标识。

商品下架、不匹配只影响展示，不改成 EXITED／REMOVED、不释放有效参与名额、不递增报名轮次。重新符合条件时先核对仍在有效专题、关系仍为 JOINED、禁报已解除及所有当前公开条件，再恢复展示。`matches_conditions` 只表示最近记录结果，不能绕过当前真实资料检查；解除移除后即使匹配，也必须先主动重报。

报名、退出、移除、解限、当前条件结果及事件日志在同一数据库事务内成功或回滚；校验专题发布、时间、整体隐藏、商品归属与上架、经营权限、现有限制和过滤条件。报名不检查必须有库存，缺货展示不等于库存预订。

相关服务统一锁顺序：先按专题ID升序锁定涉及的专题，再锁商品，再锁参与关系；商品批量变更先发现相关专题集合，取得锁后重新核验集合，如发现并发新增关系则整体回滚重试，不能遗漏其条件日志。涉及单个商品的助农信息操作只锁该商品及其推广记录。统一设置有限事务重试，死锁或版本冲突后以原幂等键重试，不保留半次事件。

### 条件历史 JSON 与结束事实

日志的 `before_snapshot`／`after_snapshot` 为 JSON 对象，首次 JOIN 的前值为空，其余有前后值。下列结构是后端固定白名单，不能从客户端原样接收；BIGINT ID 在 JSON 中统一用十进制字符串，避免 JavaScript 精度丢失。

```json
{
  "schema_version": 1,
  "participation": {
    "round": 1,
    "status": "JOINED",
    "joined_at": "2026-11-19T02:00:00.000Z",
    "left_at": null,
    "is_join_blocked": false,
    "blocked_event_seq": null
  },
  "product": {
    "id": "101",
    "origin_region_id": "500101",
    "origin_ancestor_ids": ["500000", "500100", "500101"],
    "category_id": "12",
    "category_ancestor_ids": ["1", "12"],
    "is_listed": true,
    "is_admin_blocked": false
  },
  "campaign_filter": {"region_id": "500000", "category_id": "1"},
  "matches_conditions": true,
  "farmer_operating": true
}
```

- 祖先数组含自身，按根到当前节点排列；保存当时实际使用的节点路径与匹配结果，避免今后只看当前商品字段或变动后的字典树，无法解释过去条件。
- 商品快照中的 `origin_region_id`／`category_id` 对应真实商品同名字段；`is_listed` 由 `product.listing_status=ON_SHELF` 得出，`is_admin_blocked` 由 `product.admin_blocked=1` 得出，`farmer_operating` 由 `farmer_profile.status=ACTIVE` 得出。这些只是当时事实，封禁后是否以及如何恢复仍按原业务权限及未决政策处理，不能凭单个快照布尔值授予恢复操作。后端固定快照键集合并限制序列化大小不超过16 KiB，禁止混入任意描述、完整商品或用户资料。
- 参与仍保留且专题尚未有效结束时，修改商品产地／分类必须对所有相关参与追加前后快照，即使改动前后都匹配也记录，因为具体来源事实已变。更新商品、关系匹配结果和日志必须同事务提交；不得只在可见性发生改变时记一条日志。
- 相关上下架事实变化同样写事件；权限限制的进一步业务联动仍按未决项处理，保存事实不等于授权额外退出、结束或恢复。字典节点迁移、停用若后续开放，必须先明确联动政策并保证旧路径快照不被覆盖，不能只改字典树后默默重算历史。
- 事件时间表示实际生效时刻，`created_at` 是落库时间。每个关系按 `event_seq` 确定同一毫秒内顺序，不依赖全局自增ID作为跨事务提交顺序。有效操作的时间在持有业务锁、再次确认资格后采样。
- 专题首次有效结束时，为已有关系保存 `end_effective_at`、`end_event_seq`、`end_snapshot`，快照沿用上述 JSON 结构。它保存当时事实，**不存“是否属于公开历史成员”的新政策字段**。已退出或已移除关系也保留事实；正常结束后的后续资料变化不得覆写此快照。
- 提前结束持有专题锁，阻止新的参与变更，冻结各关系最后有效事件及事实；这能区分同一毫秒内发生在结束动作之前的有效操作。自然结束按原截止取事件事实，截止时刻及之后不再接受进行中操作；延迟任务按该时点回溯，不能采集任务执行时的新商品资料充当过去事实。
- 专题整体隐藏不清空这些事实。只因农户下架隐藏的原有效参与按已确认规则保留历史资格；**因分类／产地不匹配隐藏的结束历史纳入与公开规则仍未决**。字段保存事实以便后续制定规则，不默认纳入或排除，也不提前生成公开历史响应。
- 现有关系及结束事实足以回溯时不再新建历史成员表。后续若开放结束后的其他管理动作，仍须保留原截止快照，只单独判断当前公开限制。

### 主动助农信息与七天重发

`assistance_post` 不设草稿审核或待审状态。成功提交即形成一条已发布记录；发布时间、关联商品和截止不可改。选填 `buyer_type` 设计为 HOUSEHOLD／BULK／BOTH，也可 NULL；这是展示偏好，不建立采购意向单或不同交易路径。供货时间采用普通短文本，与推广截止独立。

- `end_source` 空值表示结束事实尚未落库，不能据此断言当前仍有效；NATURAL 表示自然结束，FARMER 表示农户主动结束。自然结束时间精确等于固定截止，主动结束在截止前并保存实际操作者，不要求额外必填理由。
- CHECK 保证 `published_at < deadline_at <= published_at + 30×24小时`；应用使用 UTC 时间点计算，不按自然月或本地日期午夜判断。极端超出 DATETIME 可表达范围的输入由接口拒绝。
- 创建、编辑、主动结束和到期补处理均锁 `product` 行后再锁该商品推广记录，按商品串行校验。不能用“不在公开列表”代替“已结束”，也不能仅用 Redis 锁保护。
- 在同一事务内读取该商品所有尚未落库结束的记录，按截止补齐自然结束；若存在未到期且未主动结束的记录则拒绝新建。隐藏中的未结束记录仍占名额。检查最近一轮有效正常结束时间，必须满足 `now >= effective_end + 7×24小时`；首次发布没有等待期。
- 延迟任务的 effective_end 必须取旧截止，不取当前执行时间；新建事务也执行相同补判，避免多等七天或跳过等待。选取最新一轮不能任取更早历史。重发创建新行，不复活旧行。
- `product_id` 只建普通检索索引，不建终身唯一键。单条有效名额和七天等待是跨记录时间约束，由上述商品行锁事务完成。
- 创建幂等键使用 `farmer_id + request_id`，`request_fingerprint` 保存规范化原发布输入的 SHA-256 摘要，后续编辑不覆盖。相同键不同原始输入返回冲突；相同输入重试成功请求返回原记录，不刷新发布时间；新一轮重发使用新键。编辑只能更新标题、推广说明、供货说明与买家类型，并核对版本、未结束和截止；到期或结束后拒绝旧编辑。
- 农户上下架与经营权限、商品限制按关联对象实时判断，不在本表新增可以独立覆盖它们的公开开关。正常结束历史可公开原说明，但关闭旧条新增咨询；产品价格、库存和入口仍按当前商品规则返回。管理员下架等未决联动不被设计成新的正常结束来源。

### 产地图文结构与管理

`origin_content` 一地区一份，经管理员权限和内容校验后保存即可展示，不新增投稿审批、文章列表、社区评论或任意 HTML 编辑。`content` 与农户 `story_content` 使用同一种有序 JSON 块数组：

```json
[
  {"type": "text", "text": "这里填写维护者提供的产地介绍。"},
  {"type": "image", "key": "uploads/demo/origin.jpg"}
]
```

本轮与农户故事统一采用最多50块、总文字最多10000字符；产地图文再限定最多20张图片、每文字块最多1000字符，至少一块有效内容。SQL 只检查非空数组及总块数，后端校验块对象仅包含对应白名单字段、文字非空、所有图片资源有效且可用，并限制请求大小。文本按纯文字渲染，不执行 HTML、脚本或模型指令；图片 key 不接受任意外链和目录穿越。若前端支持图文编辑器，也必须输出相同受控结构。

首次发布时间固定，后续编辑通过版本条件更新。删除、隐藏、恢复等未决操作不因这张表存在就自动开放，表中不预设未确认的审核或撤回状态。内容事实来源于维护者，不虚构实地认证。

## 留言、推广统计、AI 与管理日志

### 留言会话与文字消息

关联需求：FR-COMM-001、FR-COMM-002。`consultation_thread.user_id` 关联 `sys_user.id`，`farmer_id` 关联 `farmer_profile.id`。`consultation_message.thread_id` 关联会话，`sender_user_id` 关联平台账号，来源字段分别关联商品、专题、助农信息。本版不使用物理外键，存在性、归属与可操作状态由服务端校验。

本轮采用“同一咨询用户与同一农户共用一个会话”的常规实施设计，唯一键 `user_id + farmer_id` 阻止重复会话；不将此说成过去已由用户选择。用户以后咨询同一农户的其他商品，在同一会话内发送带新商品来源的消息。`sender_side` 为 `USER` 或 `FARMER`，服务端必须分别校验发送人等于 `thread.user_id` 或 `farmer_profile.user_id`；拥有农户身份不使其在所有会话都变成接收方。

- 发送事务先锁会话行，分配 `last_seq + 1`，插入消息并更新 `last_seq / last_message_at`；同一毫秒内的消息依靠序号排序。`thread_id + seq` 唯一。
- `client_message_id` 在单会话、单发送账号范围内唯一。重试返回原消息；同标识不同内容或来源应拒绝，不多发消息、不重复记推广事件。
- 已读位置只向前推进且不能超过已提交 `last_seq`；未读为对方发送、序号大于本侧已读位置的消息数，不直接用 `last_seq - read_seq` 作为未读数。
- 只存普通文字，长度上限 2000 字符是本轮实现值；禁止把内容作为 HTML 执行。没有 WebSocket、在线状态、已送达回执或采购意向状态机。
- 消息的 `source_type` 允许 `DIRECT`（既有会话直接发送）、`FARMER`（农户主页）、`PRODUCT`、`CAMPAIGN`、`ASSISTANCE`；后三者带商品，专题和助农信息来源二选一。引用必须属于接收农户，专题来源须验证有效参与，助农信息来源须验证有效可用；不得只凭客户端填写 ID 记来源。
- 从历史已结束助农信息不能新发咨询；正常已存在会话的后续留言按既有访问权限处理，不重新伪装成一次旧推广入口咨询。管理禁用对存量会话的权限按相应模块未决规则处理，字段不预先授予额外权限。
- 已发送消息保留原来源供双方理解与统计，不因商品改名、退出专题或正常结束推广而改写；展示入口仍校验当前访问权限。

### 推广事件与首版统计口径

关联需求：FR-PROMO-003。`promotion_event` 的关联均为服务端确认的事件事实，不是可由客户端自由填写的统计接口。`user_id` 与 `visitor_hash` 恰有一个非空；匿名标识来自应用随机访客 ID 的哈希，不采集设备指纹，也不把其认作真实自然人。

本轮采用以下实现口径，后续如调整需同步接口和报表名称：

| 事件 | 本轮计数方法 | 去重与归属 |
| --- | --- | --- |
| `VIEW` | 同一已登录账号或匿名访客、同一来源对象，在服务端 UTC 的同一 30 分钟桶内计一次 | `event_key` 为规范化事件类型、来源对象、观察者和时间桶的 SHA-256；只能在成功读取允许公开的详情后生成 |
| `CONSULT` | 成功保存、来源已校验的买家文字消息计一次，称“咨询消息数” | `event_key` 基于消息 ID；`consultation_message_id` 唯一。农户回复和 `DIRECT` 续聊不新增推广咨询事件 |

来源对象为农户主页、商品、专题或助农信息；从专题进入指定商品时以“专题＋商品”作为独立来源维度，不能与专题页本身混成一条。专题页浏览若未指向具体农户，`farmer_id/product_id` 均为空，只进入平台专题汇总；不能把一次专题浏览乘以全部参与农户。一个事件只有一种直接来源，不将商品同时参加的所有专题都记功。买家在带有效来源的消息后继续 `DIRECT` 对话，不将每轮回复继续归因给旧入口。事件入库按唯一键幂等，咨询消息与其事件在同一事务保存。

报表显示“去重浏览次数”“咨询消息数”，不显示为浏览人数、独立咨询人数、采购意向、成交或真实助农收入。浏览和咨询可以按来源、农户、时间分别聚合，不把不同来源维度的去重浏览简单解释为平台独立访客。日视图边界由服务端按 `Asia/Shanghai` 换算 UTC 查询范围；事件自身保存 UTC，去重时间桶固定使用 UTC。

### AI 会话、展示消息与调用记录

关联需求：FR-AI-001 至 FR-AI-007。`ai_conversation.user_id → sys_user.id`，`ai_message.conversation_id / ai_usage_log.conversation_id → ai_conversation.id`；调用记录的 `user_id` 必须与会话所属账号相同。每次发送前校验登录、账号状态和会话归属，管理员日志不自动获得读取全部私密聊天的权限。

- 会话 `status` 为 `ACTIVE`（可以继续对话）或 `CLOSED`（不能继续）；该存储能力不是新增归档／删除产品入口。关闭原因、历史保留期限及用户删除权限在 AI 模块落实，不能从字段默认推导为永久保留。
- 消息 `role` 仅 `USER / ASSISTANT`，保存用户提问及最终允许展示的回复；系统提示词、内部工具完整参数与结果不复制为可见消息，不保存模型隐藏推理。消息 `status` 为 `PENDING / COMPLETED / FAILED / REJECTED`。
- 一次业务 `request_id` 在会话内最多一条用户消息和一条最终导购消息，重试使用同标识检查原请求内容；不同内容不可复用。序号在会话锁内分配并更新 `last_seq`，生成可先建立待完成的导购行，再更新内容与结果，不能长时间持有数据库事务等待云端回复。
- 同一业务请求仍在进行时，客户端重试只查询或订阅原结果，不重新启动收费流程；终态请求的同标识重试也返回原结果。内部工具轮次或受控重试由持有该请求执行权的后端流程分配新的 `call_no`，不能由重复 HTTP 提交自行增加调用。
- `recommended_product_ids` 为商品 ID 字符串数组，例如 `["101", "102"]`；必须由后端核验，不能直接采用模型任意 ID。读取历史时再次校验当前商品公开状态，卡片当前价格库存重新查询，不把历史文本当成下单依据。JSON 数组元素类型、长度、去重由应用验证，数据库只检查数组形状。
- 消息内容使用 `TEXT` 只是持久化容量，不代表放开输入、上下文或输出 token 上限；这些限制由已配置的后端规则独立执行。未选定的示例参数不固化为数据库配额。
- `ai_usage_log` 按每次内部模型调用建行，`call_id` 全局唯一；`conversation_id + request_id + call_no` 唯一，一次提问可有多个调用。重试、工具后续调用和收费意图识别各占一条；本地固定拒绝无需伪造一条零费用的模型调用。

| 维度 | 值与含义 | 注意事项 |
| --- | --- | --- |
| 调用 `status` | `PREPARED` 已登记待发送；`RUNNING` 已开始请求；`SUCCEEDED` 收到有效响应；`FAILED` 明确失败；`UNKNOWN` 超时／中断等导致结果不明 | 失败或未知不等于未收费；进程崩溃的在途调用须恢复核对 |
| `usage_source` | `UNKNOWN` 无可用用量；`ESTIMATED` 本地估算；`PROVIDER` 上游报告 | `input_tokens / output_tokens` 未知为 `NULL`；0 只在确认零时写入。部分分项缺失仍为 `NULL`，不能补零 |
| `cost_source` | `UNKNOWN` 无费用数据；`PRICING_ESTIMATE` 按配置估算；`PROVIDER` 上游或可靠账单报告 | `estimated_cost` 与 `reported_cost` 分列，估算不冒充实付；上游报告时可同时保留原估算 |
| `budget_state` | `RESERVED` 已预留；`UNRESOLVED` 用量或收费待核对，保留占用；`SETTLED` 按可信依据完成预算记账；`RELEASED` 确认未发生收费后释放 | 预算记账可以基于完整用量和价格的估算，仍不是账单结算证明；不因超时或缺少 usage 自动释放 |

`usage_details` 是白名单数值对象，例如 `{"cachedInputTokens": 200, "reasoningTokens": 100}`；缺少分项时省略，不存完整上游响应。不同平台的缓存／推理计入输入输出方式不同，适配层说明口径，不能盲目再次相加。

`pricing_snapshot` 是计价配置对象，例如 `{"unitTokens": 1000000, "inputPrice": "10.00000000", "outputPrice": "30.00000000", "basis": "EXAMPLE"}`。**这只是结构示例，不是实际价格或默认配置。** 真实配置要覆盖所选平台的缓存、推理和附加费用，并记录 `pricing_version`；未知附加计费不能据此声称精确总费用。快照不含 Key、账号余额、敏感 URL 或鉴权头。`currency` 使用大写三字母币种代码，同一行所有金额同币种；不同币种不能直接累加，平台首版预算须配置与供应商一致币种，未配置时不启动收费调用。

预算事实与事务约束：

1. 每个外部调用前，后端按已配置最大消耗计算 `reserved_cost`，完成原子预算检查，登记 `PREPARED` 并使 `accounted_cost = reserved_cost` 后才能发送。预留不能仅存在 Redis；DB 与 Redis 协调失败时不发起该次外部请求。
2. 记录 `RUNNING/started_at` 后调用模型；结束时记录状态、usage 和费用来源。`accounted_cost` 是本条当前应占用的总额，汇总时不能再加一次 `reserved_cost`。未决状态保留至少原预留；获得可信数据后按规则将其替换为结算占用，而非重复累加。
3. 用量未知或不足以核实费用时转 `UNRESOLVED`，禁止按空值补零释放；能够确认调用未发送或未收费才可 `RELEASED`。可靠账单显示超出预留时如实提高记账占用并阻止后续超预算调用，不截断到预留值。
   预算预留后、实际发送前发生本地失败，可写 `FAILED` 与 `finished_at`，保持 `started_at` 为空；确认未发送后释放预留。已经发送但结果不明则保留 started_at，按 UNKNOWN／UNRESOLVED 处理，不能伪装为未发送。
4. 本地平台额度、周期、实际模型价、并发锁／Redis 原子脚本及对账程序仍在工程阶段落实；本表提供恢复事实，不单靠 `SUM` 查询完成并发防超支。Redis 丢失不得清空既有费用，应先从 MySQL 恢复占用再开放收费调用。
5. 费用记录不随用户消息清理而自动级联删除；历史保留期限、脱敏／删除策略仍见 AI 待确认项。隐私策略落地时需协调会话引用和必要用量留存，不把表存在解释为无限期保存全部聊天。

### 管理员操作日志

关联需求：FR-ROLE-001 及各管理操作。`admin_user_id → sys_user.id`，服务端确认有效管理员身份；`target_type + target_id` 为受控的多态关联。目标类型对应：`USER → sys_user`，`FARMER_APPLICATION → farmer_application`，`FARMER → farmer_profile`，`PRODUCT → product`，`CATEGORY → product_category`，`REGION → region`，`CAMPAIGN → campaign`，`CAMPAIGN_PRODUCT → campaign_product`，`ASSISTANCE_POST → assistance_post`，`ORDER → trade_order`，`REFUND_REQUEST → refund_request`，`REVIEW / REVIEW_REPLY → order_review`，`ORIGIN_CONTENT → origin_content`。列出类型只表示日志可以关联，不新增尚未批准的管理操作权限。

`operation_id` 防止同一操作重复记成功日志；动作代码由服务端白名单产生。重要成功操作与日志在同一业务事务提交；如另记失败事件，使用独立事件 ID，并在业务回滚后写入，不伪装成已发生的修改。订单／退款过程仍需 `order_action_log`，管理审计不能替代原业务日志。

`changes` 为脱敏对象，例如 `{"status": {"before": "VISIBLE", "after": "HIDDEN"}}`；按动作白名单记录必要状态／标识，不复制整条用户记录、手机号、详细地址、密码哈希、密钥或完整聊天。`result` 为 `SUCCESS / FAILURE`。限制、隐藏、恢复等已要求原因的动作在服务端强制填写 `reason`；字段可空是为其他无需原因的操作，不能绕过已有必填规则。日志只追加，不向普通管理页面提供随意改删历史的入口。
