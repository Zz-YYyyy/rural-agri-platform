归档约定：

- `docs/` 内的文档使用能直接说明用途的中文文件名；后续新增文档也遵循此约定，改名时同步更新链接和路径引用。文件名称不改变正文标明的确认、设计或实现状态。
- 同一份正式说明只维护一处，其他目录通过链接引用；后续新增的开发、部署或运行说明也归入 `docs/`，按实际需要分类，不在工作区外层另建重复文档树。
- 仓库根目录的 `README.md` 保留项目介绍和入口，`AGENTS.md` 保留供开发者与 AI 使用的开发约定；各代码、部署和脚本目录可保留简短 README，详细项目文档集中到此处。
- 可执行 SQL、迁移脚本、部署配置及源码仍放各自工程目录；`docs/` 保存对应设计与使用说明，不复制一套可执行文件。

## 第一次接手项目的阅读顺序

1. 阅读仓库 [README](../README.md) 和 [开发约定](../AGENTS.md)，了解目录、当前进度和文档同步规则。
2. 先读功能模块与主要页面总览了解产品全貌，再按模块阅读需求确认稿及决策记录，理解对应 `FR-` 的角色和核心规则。
3. 阅读待确认问题和页面与导航说明，区分已确认入口与仍待讨论的布局、操作和访问策略。
4. 阅读技术设计及验收场景，理解一致性约束、AI 数据边界和预期行为。
5. 接手具体模块时再阅读接口、数据库和后续部署文档，核对这些内容是否已经完成设计及与当前代码一致。

不要求后续开发者读取历史聊天才能补齐关键规则。重要结论应当在仓库内可定位；若仍有缺口，先查对应问题编号，再向用户讨论，不能自行把未决业务方案写成既定事实。

阅读编号时同时核对状态和后续替代决策；保留在历史／后续扩展章节中的编号不表示当前仍需实现。

## 编号与追踪方式

| 标识 | 含义 | 维护位置 |
| --- | --- | --- |
| `FR-` | 已确认需求或业务规则 | 需求确认稿 |
| `Q-` | 尚待用户确认的问题 | 待确认问题清单 |
| `P-` | 页面讨论标识 | 页面讨论稿，暂不代表最终路由名 |
| `D-` | 已确认决策记录 | 决策记录 |
| `AC-` | 验收场景 | 验收清单，是否通过另有执行记录 |

后续接口和数据库设计需引用对应 `FR-`、关联数据与 `AC-`。例如 FR-INV-001 应能追踪到下单、取消和退款接口的库存效果、库存数据与事务约束，以及 AC-INV-001 等验收场景。这里的关联关系是编写要求，不代表相关接口和表已经存在。

## 文档形成与变更顺序

1. 收拢功能模块、主要页面与流程，集中确认影响功能范围和核心业务的剩余选择，及时更新需求与决策。
2. 写清核心状态、输入、权限及必要异常，设计数据库与接口；常规实现细节由开发确定，不为每个字段或罕见组合另开一轮讨论。
3. 把已完成设计的模块与未决模块明确分开，不能将未决业务猜测写入可执行契约或迁移脚本。
4. 按确认后的模块开发和验证。行为、请求响应或数据结构有变化时，同步更新受影响文档、契约、测试与迁移。

状态用词统一：**已确认**表示用户已选择或认可；**建议／待确认**表示仍需讨论；**已设计**需具备足够规格；**已实现／已验证**需有代码与相应验证证据。当前没有应用运行或验收通过记录。
